This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Package manager is **pnpm**; the workspace is wired up with **Turbo**.

- `pnpm dev:electron` – Electron + renderer with live reload (the primary dev loop). Runs `build:native` and `write-main-hash-dev.js` as pre-steps.
- `pnpm dev` – Vite dev server for the renderer only (browser preview, web-UI mode). Proxies `/api/v2` to `http://10.0.0.32:18888` (see `vite.config.ts`).
- `pnpm build` – Renderer-only build (the artifact published as the qBittorrent "alternative Web UI" tarball).
- `pnpm build:electron` – Full desktop build: `build:native` → `electron-vite build` → `electron-forge make`.
- `pnpm build:render-release` – Renderer build with `ELECTRON_RENDER_BUILD=1` (used inside the Electron build pipeline; switches the platform-specific import plugin and `__WEB_UI__`).
- `pnpm typecheck:turbo` – Type-check every workspace package via Turbo. Also `pnpm typecheck:main` / `pnpm typecheck:renderer` for a single package.
- `pnpm lint` / `pnpm format` – ESLint --fix / Prettier write. Pre-commit runs lint-staged on staged JS/TS/JSON.
- `pnpm license:check` / `pnpm license:update` – Vendored-license audit and refresh.

There is **no unit test suite** in this repo. "Tests passing" means `pnpm typecheck:turbo` + `pnpm lint` are clean, plus manual QA via `pnpm dev:electron` (and the browser preview when the change touches web-UI mode).

`ANALYZE=1 pnpm build` enables `vite-bundle-analyzer`.

## Architecture

### Workspace layout

This is a pnpm + Turbo monorepo. Workspace globs are `layer/*` and `packages/*` (see `pnpm-workspace.yaml`); `portal/` is a separate sub-workspace (Vercel deployment) and is **not** part of the desktop build.

- `layer/main` (`@torrent-vibe/main`) – Electron main process. Entry `src/index.ts` → `bootstrap.ts`.
- `layer/renderer` (`@torrent-vibe/renderer`) – React 19 + Vite + Tailwind v4 UI. Three HTML entries: `index.html` (main window), `mini.html`, `panel.html`.
- `packages/qb-client` – Thin wrapper around `@innei/qbittorrent-browser`. Used by both main and renderer.
- `packages/shared` – Cross-process types/utilities (AI, app errors, update payloads, API tokens).
- `plugins/vite` – Custom Vite plugins: `cleanup`, `deps` (vendor chunking), `i18n-hmr`, `specific-import`.
- `plugins/eslint` – Custom ESLint rules that validate `locales/**/*.json`.
- `scripts/` – Build, signing, update-manifest, license, and main-hash tooling.
- `native/` – `build-all.sh` walks subdirs and runs each `build.sh`; pre-step for both `dev:electron` and `build:electron`.

### Two build modes for the renderer

The same React code ships as both the Electron renderer and a standalone web UI. The split is controlled at build time:

- `vite.config.ts` is the base config used by `pnpm dev` / `pnpm build` (web UI). It sets `__WEB_UI__ = true`, `ELECTRON = false`, and skips the `electron` platform-specific-import pass.
- `electron.vite.config.ts` extends it for `dev:electron` / `build:electron`. It sets `__WEB_UI__ = false`, `ELECTRON = true`, and inserts `createPlatformSpecificImportPlugin('electron')`, which rewrites imports based on platform suffixes (e.g. `foo.electron.ts` vs `foo.ts`). Files like `router.electron.tsx` exist precisely to be picked up by this plugin.

When touching renderer code that uses Electron-only APIs, prefer the `*.electron.ts` suffix pattern over `ELECTRON ? ... : ...` runtime checks.

### Main ↔ renderer IPC

IPC uses `electron-ipc-decorator`:

- Each service lives in `layer/main/src/ipc/*.service.ts` as a decorated class.
- `layer/main/src/ipc/services.ts` registers them all and exports the `IpcServicesType` type via `@torrent-vibe/main`.
- The renderer imports that type in `layer/renderer/src/lib/ipc-client.ts` to build a typed proxy: `ipcServices.someService.someMethod(...)`. This is the only sanctioned way to call into main.

To add a new IPC surface: create a `*.service.ts` in `layer/main/src/ipc/`, register it in `services.ts`, then call it via `ipcServices` in the renderer.

### Routes

Renderer routes are auto-generated by `vite-plugin-route-builder` from files under `layer/renderer/src/apps/main/pages/**/*.tsx` into `generated-routes.ts`. **Do not edit `generated-routes.ts` by hand.** Pages use the `(group)` folder convention. There are separate `router.tsx` (web) and `router.electron.tsx` (Electron) variants resolved by the platform-specific-import plugin.

There are three renderer apps (each with its own HTML entry): `apps/main`, `apps/mini`, `apps/mini-panel`.

### Store + Actions pattern (mandatory for complex modules)

Any feature with shared state and async side-effects (modals, dashboards, wizards) MUST follow the pattern documented in `docs/store-actions-pattern.md`:

1. `store.ts` is a Zustand store (`createWithEqualityFn` + `subscribeWithSelector` + `immer`) that holds only serializable state. No async, no business rules.
2. A singleton `*Actions` class encapsulates every side-effect, returns `{ ok, data?, error? }`, and uses request tokens to guard against stale responses.
3. UI components subscribe with selectors and call actions on events; they never mutate the store directly and never emit toasts from actions (toast/i18n mapping happens in the UI).

Reference implementations: `layer/renderer/src/modules/discover` (`docs/discover-modal-architecture.md`) and the AddTorrent modal (`docs/addtorrent-modal-architecture.md`). For trivial components, local `useState` is still fine.

### Persistence in main

The main process owns a SQLite database (`layer/main/src/services/database/` – schema, migrations, app-database) using `sqlite3` + Drizzle ORM. App settings and API tokens have dedicated stores under `services/`. Updates and AI live in `services/update-service.ts`, `services/github-update-service.ts`, and `services/torrent-ai/`.

Managers (singletons in `layer/main/src/manager/`) own runtime concerns: windows, deeplinks (`magnet:`), file-open, tray, session/CORS, single-instance, content loader, and the hot-update content loader. CORS / web security is intentionally disabled at the Chromium command line — see `bootstrap.ts`.

### Logging

`electron-log` with per-service scopes. Use `getLogger('Scope')` from `layer/main/src/config/log-config.ts`. Logs land in the userData logs directory (`~/Library/Logs/torrent-vibe/` on macOS); see `docs/logging-guide.md`.

## Conventions

- **TypeScript + ESM** everywhere. Strict mode, but `noImplicitAny` is off.
- **File names**: React components `PascalCase.tsx`; modules/utilities `kebab-case.ts`. Platform-specific variants use `name.electron.ts` (resolved at build time, not runtime).
- **Tailwind v4**: prefer utility classes. Tailwind is configured via the `@tailwindcss/vite` plugin and PostCSS, not a config file.
- **ESLint**: based on `eslint-config-hyoban` with repo-specific tweaks (see `eslint.config.mjs`). Notably, `location` is banned globally — use `useLocation` or `getReadonlyRoute` because the Electron/browser routers are distinct instances.
- **i18n**: JSON in `locales/{app,native,setting}/{en,zh-CN}.json`. Custom ESLint rules enforce sort order and key parity — run `pnpm lint` after editing translations. **Never create both a parent key and child keys with the same prefix** (e.g. don't have both `foo.bar` and `foo.bar.baz`; use `foo.bar.default` as the leaf).
- **Settings modal tab naming**: `appearance`, `appPreferences`, `appConnection` (web-only), `servers` (Electron-only).
- **Path mapping (Electron Servers tab)**: edits go through `PathMappingModal` via `Modal.present`; the first matching mapping wins, so drag-handle order is significant.
- **Commits**: Conventional Commits (`feat:`, `fix:`, `refactor:`, `chore:`…). `simple-git-hooks` runs lint-staged on pre-commit (Prettier + ESLint --fix).
- **Env config**: copy `.env.example` to `.env`. Trial/Pro is a runtime license decision; there is no separate `NODE_ENV=trial` build. Production builds may set `SECURITY_OBFUSCATION=1`.
